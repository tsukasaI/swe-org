# Search in Rotated Sorted Array (33)

- **Date**: 2026-04-25
- **Context**: arai60 LeetCode practice — coding interview prep
- **Goal**: ローテートされたソート済み配列から target を一発二分探索で探す

## Memorize

- ループ条件は `l <= r`（特定の値を探す標準パターン）
- mid を見たら必ず `nums[m] == target` を最初にチェックして即 return
- **左右どちらか必ずソート済み** → `nums[l] <= nums[m]` で左ソート済みを判定（**`<=` 必須**）
- ソート済みの半分で target の範囲チェックして進む方向を決める
- 配列外アクセス防止のため、ループの更新は `l = m+1` / `r = m-1`

## Understand

### 計算量

- Time: O(log N)
- Space: O(1)

### なぜ「片方は必ずソート済み」と言えるのか

- 「下がる境目（回転点）」は配列に**1箇所しかない**
- mid で2分割すると、回転点は左右どちらか**1つの半分にしか入らない**
- 回転点を含まない側は元のソート順がそのまま残る → ソート済み
- ポイント: 「回転点が1箇所」と「2分割すると片方にしか入らない」を結びつけて説明できること

### `<` ではなく `<=` を使う理由

- 重複要素のためではない（問題の制約「全要素ユニーク」なので重複は出ない）
- 本当の理由: `l == m` のケースをハンドリングするため
- `l == m` のとき `nums[l]` と `nums[m]` は**同じインデックスを参照しているので必ず等しい**
- このとき左半分は1要素（`nums[l]` 自身）でトリビアルにソート済み → 左ソート済みブランチで処理すべき
- `<` だと `nums[l] < nums[m]` が false で else（右ソート済み）に流れて誤判定
- 例: `[3,1], target=1` で `l=0, m=0, nums[l]=nums[m]=3` のとき `<` だと右ソート済みブランチに入って失敗

### なぜソート済みの半分で範囲チェックするのか

- ソートされていない半分は**両端の値だけでは中身を判定できない**（回転点による不連続性があるため）
- 例: `[7, 0, 1, 2, 4]` の両端は 7 と 4。target=5 のとき範囲 `[4, 7]` に 5 は含まれるが、実際の中身に 5 はない
- ソート済みの半分は単調増加なので「中身は必ず両端の範囲内」が保証される → 端点比較で存在判定が決定的

### なぜループ条件が `l <= r` か

- 「一致条件を探す」場合、`l == r` の最後の1要素も target と一致するかチェックする必要がある
- `l < r` だと `nums = [1], target = 1` で `l=r=0` なのでループに入らず `return -1` してしまう
- 一方 LC 153（境界探索）は最後の `l == r` がそのまま答えのインデックスになるので `l < r` で OK
- 違い: 「値そのものを探す」 vs 「条件を満たす境界の位置を探す」

### つまずきポイント

- ループ条件を `l < r` にすると `[1], target=1` で入れずに -1 を返す → `l <= r` 必須
- 右ソート済みブランチで「target が範囲外なら左に行く」を忘れて常に `l = m+1` してしまう
- `len(nums) == 1` の特別扱いは不要（`l <= r` で自然にカバー）

### コードの整理

ヘルパーで「範囲内チェック」を抽出すると見通しが良くなる:
```go
inRange := func(lo, hi, t int) bool { return lo <= t && t <= hi }
```
- `nums[m]-1` / `nums[m]+1` で「nums[m] は既にチェック済みなので除外」を明示できる

## Connect

### 81 (Search in Rotated Sorted Array II): 重複あり

- 戻り値が `bool` に変わる（インデックスじゃなく存在チェック）
- `nums[l] == nums[m]` のとき左右どちらがソート済みか判定不能
- 例: `[1,0,1,1,1]` も `[1,1,1,0,1]` も `nums[l]=nums[m]=nums[r]=1` で区別できない
- 修正: `nums[l] == nums[m]` のとき `l++` で範囲を縮める
- 最悪 O(N)、平均 O(log N)

### 153 (Find Minimum in Rotated Sorted Array): 最小値だけ

- LC 33 の代替アプローチ: 153 で回転点を見つけ → 2つのソート済み区間で標準二分探索
- 二回二分探索パターン: 実装は易しいが定数倍2倍
- トレードオフ: 一発派はコード短いが認知負荷高、二回派はコード長いがロジック単純
- 実務では「シンプル > 微小最適化」なので二回派が無難なことも多い

### 関連の二分探索パターン

二分探索は大きく2パターン:

| | 境界探索 (LC 35) | 値探索 (LC 33) |
|---|---|---|
| 不変条件 | 範囲ベース `[l, r)` | 単一要素ベース |
| ループ条件 | `l < r` | `l <= r` |
| 右更新 | `r = c` | `r = m - 1` |
| 初期 r | `len(nums)` | `len(nums) - 1` |
| 戻り値 | `l`（位置） | mid 一致時 `m`、なければ `-1` |

- 境界探索 (LC 35, 153, 278): 条件を満たす最小/最大の**位置**を探す
- 値探索 (LC 33): 特定の**値**を探す
